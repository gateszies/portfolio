## Context

[Studio Projects](https://www.whcc.com/studio/projects) help professional photographers organize gallery images and order print products for their clients at scale.

I joined the engineering team to build a component library for a multi-brand app on [Symfony's Twig Components](https://symfony.com/bundles/ux-twig-component/current/index.html), migrating it off a legacy codebase with no real component model.

---

## Problem

### Custom tags instead of real components

The legacy templates used invented tag names directly in the markup and styled them the same way you'd style a `div`.

```twig title="panel.html.twig"
<panel accountSettings>
  <panelTitle largeHeader>Project Settings</panelTitle>
  <setting name=title>
    <settingLabel smallHeader>Title</settingLabel>
    <value>{{ project.title }}</value>
  </setting>
</panel>
```

```scss title="_panel.scss"
[accountSettings] {
  panelTitle {
    border-bottom: 1px solid $lineColor1;
  }
  setting {
    display: flex;
    flex-flow: column;
  }
}
```

This approach created accessibility gaps and ongoing maintenance costs:

- `panelTitle` isn't a real heading, so a screen reader has no way to know it's one
- Invented tags have no defined prop contract, so it's difficult to know what a tag like `panelTitle` actually accepts
- Using `pascalCase` is incorrect syntax for [valid custom elements](https://html.spec.whatwg.org/multipage/custom-elements.html)

### No shared design system

No source of truth meant that elements were frequently repeated with slightly different values in different files.

```scss title="_panel.scss"
// _panel.scss
[accountSettings] {
  panelTitle {
    color: #2b2b2b;
    font-size: 15px;
    font-weight: 600;
    letter-spacing: 0.02em;
    padding-bottom: 12px;
    border-bottom: 1px solid #e5e5e5;
  }
}

// _panelBrand.scss, same role with slightly different values
[tab="brand"] {
  panelTitle {
    color: #1f1f1f;
    font-size: 16px;
    font-weight: 700;
    padding-bottom: 14px;
    border-bottom: 1px solid #ddd;
  }
}
```

Design debt slowly accumulated with small mismatches in styling and Figma prototypes that were out of date with production.

### Triple the upkeep for multi-brand

The product runs the same interface across several brands, including a generic "unbranded" brand. The legacy approach meant maintaining near-identical copies of each page, one per brand, instead of one component with brand-level configuration:

```twig title="details.html.twig"
{# studio/, brandB/, brandC/, unbranded/ — four separate copies #}
<panel tab=details accountSettings>
  <panelTitle largeHeader>Account Details</panelTitle>
  <setting name=name>...</setting>
</panel>
```

Elements that functionally served the same purpose were stored in separate files with no single shared source of truth.

## Approach

### Define the pattern, not just a component

The very first PR in the project built a `Button`, but the real work was defining the pattern every component after it would follow: how props are named, how variants and colors are handled, and how tokens are structured per brand.

```twig title="Button.html.twig"
{% props
    text = '',
    color = 'brand',
    variant = 'primary',
    rounded = false,
    icon = null,
%}

{% set classNames = [
    'Button',
    'Button--' ~ color ~ variant|title,
    rounded ? 'Button--rounded',
]|filter(class => class)|join(' ') %}

<button type="button" class="{{ classNames }}">
  {% if icon %}
    <twig:Core:Icon :name="icon" />
  {% endif %}
  <span class="Button-label">{{ text }}</span>
</button>
```

Props got a consistent naming convention (`color`, `variant`, boolean variables like `rounded`) that every component built afterward could reuse.

Class names resolve in a filtered array above the markup to keep the template clean.

**Tokens were organized in three tiers:**

- Primitives → raw values unique to each brand, e.g. `--color-purple-8`
- Semantic tokens → mapped to brand-specific primitive via `[data-brand]`, e.g. `--bgColor-brand-primary`
- Component tokens → private to a single component and resolved from the semantic layer, e.g. `--_button-bgColor`

```scss title="_tokens.scss"
// Primitives, raw values per brand
[data-brand="brandA"] {
  --color-purple-8: #5b2d8e;
  --radius-none: 0;
}

[data-brand="brandB"] {
  --color-green-8: #1f6b4a;
  --radius-sm: 4px;
}

// Semantic, roles map to those primitives
[data-brand="brandA"] {
  --bgColor-brand-primary: var(--color-purple-8);
  --borderRadius: var(--radius-none);
}

[data-brand="brandB"] {
  --bgColor-brand-primary: var(--color-green-8);
  --borderRadius: var(--radius-sm);
}

// Component, private tokens resolve from semantic
.Button {
  background-color: var(--_button-bgColor);
  border-radius: var(--_button-borderRadius, var(--borderRadius));
}

.Button--brandPrimary {
  --_button-bgColor: var(--bgColor-brand-primary);
}

.Button--rounded {
  --_button-borderRadius: 50%;
}
```

### Extend pattern to interactivity

`Dropdown` was the first component that had to manage state over time. This meant wiring up a Stimulus controller, the standard way this stack pairs JavaScript with server-rendered Twig markup.

```twig title="Dropdown.html.twig"
{% props
  controller = 'core-dropdown',
  actions = {},
%}

{% set actions = {
  'toggle': 'toggle',
  'keydown': 'keydown',
}|merge(actions) %}

{% set rootAttributes = {
  class: 'Dropdown',
  'data-controller': controller,
  'data-action': 'keydown->' ~ controller ~ '#' ~ actions.keydown,
} %}

{% set triggerAttributes = {
  class: 'Dropdown-trigger',
  ('data-' ~ controller ~ '-target'): 'trigger',
  'data-action': controller ~ '#' ~ actions.toggle,
  'aria-haspopup': 'true',
  'aria-expanded': 'false',
} %}

{% set menuAttributes = {
  class: 'Dropdown-menu',
  ('data-' ~ controller ~ '-target'): 'menu',
} %}

<div {{ stimulus_controller(controller) }} {{ attributes.defaults(rootAttributes) }}>
  {% block trigger %}{% endblock %}
  <div {{ attributes.defaults(menuAttributes) }}>
    {% block content %}{% endblock %}
  </div>
</div>
```

The controller itself extends a base dropdown controller and adds what it doesn't provide: accessible keyboard navigation and keeping `aria-expanded`/`tabindex` in sync with whether the menu is actually open.

```js
import Dropdown from "@stimulus-components/dropdown";

export default class extends Dropdown {
  static targets = ["trigger", "menu", "item"];
  isOpen = false;

  toggle() {
    super.toggle();
    this.isOpen = !this.isOpen;
    this.update();
  }

  keydown(event) {
    if (!this.isOpen) return;

    switch (event.key) {
      case "ArrowDown": // ...move focus to next item
      case "ArrowUp": // ...move focus to previous item
      case "Home": // ...move focus to first item
      case "End": // ...move focus to last item
      case "Escape": // ...close and return focus to trigger
      default:
        return;
    }
  }

  update() {
    this.triggerTarget.setAttribute("aria-expanded", this.isOpen);
    this.itemTargets.forEach((item) => {
      item.setAttribute(
        "tabindex",
        item === document.activeElement ? "0" : "-1",
      );
    });
  }
}
```

### Ship Storybook coverage alongside the component

In the legacy codebase, there was no documentation beyond the code itself. Visually previewing elements meant reading the Twig and CSS, spinning up the local dev environment, or checking whatever happened to be live on dev, stage, or prod at the time.

```js

export const WithoutIcons = {
```

## Key Decisions

### Invest disproportionately on the foundation, on purpose

Building the first `Button` component and setting up the tokens took longer than almost any other work I did on this project. I did it deliberately, as whatever patterns we set there would ripple out to everything built afterward. The cost of getting it right early was worth paying _once_ instead of paying in small increments over and over on every component that followed.

### Keep components dumb

A component only needs to know what it's been given and how to display it. A `Card` doesn't need to know why an image is missing, only whether one is. Pushing decisions and business logic up to the caller keeps every component simple enough to reason about on its own.

### Don't reinvent common patterns, only customize where there's a real gap

`Dropdown` started from an existing base rather than being built from zero. The only things custom built were the pieces that the base didn't already handle correctly: real keyboard accessibility and focus management. Customization was spent closing actual gaps, not rebuilding what already worked.

## Impact

Studio Projects runs on real, reusable components with a fully integrated design system. Contributors are able to quickly iterate on new features with a consistent design language and a shared understanding of how to use the components.
